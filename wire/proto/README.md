# `tabula.wire.v1` — chat-channel wire schema

This directory holds the **single source of truth** for messages
exchanged over the Tabula chat channel. The schema is defined in
[`chat.proto`](./chat.proto) under the `tabula.wire.v1` package.

> Parent epic: [#13 — E2E encrypted chat (Noise + protobuf)](https://github.com/tabula-project/tabula/issues/13)
> Implementing issue: [#16 — Define `tabula.wire.v1` protobuf schema](https://github.com/tabula-project/tabula/issues/16)
> Layout: canonical `wire/` layout from [#57](https://github.com/tabula-project/tabula/issues/57).

## What this is

The Tabula chat channel terminates inside an enclave at a server that
pipes plaintext to a `claude` CLI subprocess and streams responses
back. Both sides marshal/unmarshal a small set of protobuf messages
(`ClientFrame`, `ServerFrame`) and feed the bytes through a Noise XX
transport stream over plain TCP.

This directory exists so that schema changes are reviewed in one
place. Server code (`tabula_wire.server`, future), client code
(`tabula_wire.client`, future), and integration tests all import the
generated bindings from `tabula_wire.proto.v1`.

## What this is NOT

- **Not a gRPC service.** The `service Chat { rpc Session(...) }`
  block in `chat.proto` is **documentation-only** — it captures the
  intended bidirectional-stream shape so readers can see it at a
  glance. Actual transport is **raw TCP + Noise + length-prefixed
  proto bytes**. No gRPC runtime is involved.
- **Not the framing layer.** The wire format on TCP is:
  ```
  | 4 bytes BE uint32 length | <length> bytes serialized proto |
  ```
  The length-prefix read/write loop lives in the server/client
  sub-issues (#20, #27) — not here. The framing format is documented
  here so both sub-issues agree on it.
- **Not the Noise layer.** Noise XX handshake + transport encryption
  is wrapped *around* this framing. See sub-issue #18.

## v1 contract (frozen on merge)

The schema is **frozen at v1 once this issue merges**. After that,
only **additive** changes are allowed inside v1:

| Change | Allowed in v1? |
|---|---|
| Add a new field with a new field number | Yes |
| Add a new variant to an existing `oneof` (using field number 100+) | Yes |
| Add a new enum value at the end | Yes |
| Add a new top-level message | Yes |
| Repurpose an existing field number | **No** |
| Rename / retype an existing field | **No** |
| Remove a field | **No** |
| Change an enum value's number | **No** |

A breaking change requires `tabula.wire.v2` (a new proto file and a
new `package` line). The wire-level protocol version is carried in
[`Hello.protocol_version`](./chat.proto) and echoed in
`Welcome.protocol_version` so both sides can detect mismatch and
respond with `ErrorFrame { code = PROTOCOL }`.

The Python constant `tabula_wire.proto.v1.PROTOCOL_VERSION` is the
canonical value to send and to validate against.

## Layout

The `.proto` source is **flat** in this directory. Generated Python
bindings live at the canonical package path inside the `tabula-wire`
distribution:

```
wire/
  pyproject.toml                                  # tabula-wire distribution
  proto/
    chat.proto                                    # schema source. Edit this.
    build.sh                                      # regenerates bindings
    README.md                                     # this file
  src/
    tabula_wire/
      proto/
        __init__.py
        v1/
          __init__.py                             # re-exports + PROTOCOL_VERSION
          chat_pb2.py                             # generated by protoc — DO NOT EDIT
          chat_pb2.pyi                            # generated by protoc --pyi_out
  tests/
    proto/
      test_roundtrip.py                           # round-trip tests for every oneof variant
```

The `service Chat` block in `chat.proto` declares `package tabula.wire.v1`,
which is the protobuf-level package name (descriptor identity, on the wire).
The Python import path is `tabula_wire.proto.v1`. These differ by design — the
proto package name is part of the wire contract, while the Python import path
follows the `tabula-wire` distribution layout.

## Bindings policy: generated, checked in

Generated bindings live under `wire/src/tabula_wire/proto/v1/` and are
**checked into git** for the convenience of downstream code. Anyone
who edits `chat.proto` MUST re-run [`./build.sh`](./build.sh) and commit
the regenerated `chat_pb2.py` and `chat_pb2.pyi` in the same PR.

We commit the generated files (rather than building at install time)
because:

1. There is exactly one supported language (Python) for v1; multi-
   language codegen is out of scope.
2. It keeps `pip install` of downstream packages from depending on
   `protoc` being on the developer machine.
3. It keeps PR diffs honest — schema changes show up next to the
   bindings they produce.

The trade-off: PRs that touch `chat.proto` need regenerated bindings to
be reviewable, and CI should fail if the two are out of sync. Use
`./build.sh --check` for that — it regenerates into a tmp dir and
diffs against the checked-in copy, exiting non-zero if they differ.

## How to regenerate

### Prerequisites

- **`protoc`** — pinned at version **`34.1`** (libprotoc 34.1) for
  reproducible output. Newer protoc versions emit gencode that
  requires a newer Python `protobuf` runtime; if you upgrade protoc,
  bump the runtime floor in [`wire/pyproject.toml`](../pyproject.toml) to
  match.
- **Python `protobuf` runtime** — `>=7.34.0`, matching protoc 34.1.
  See `wire/pyproject.toml`.

Install protoc on macOS:
```bash
brew install protobuf
protoc --version   # libprotoc 34.1
```

Install the Python runtime:
```bash
pip install 'protobuf>=7.34'
```

### Regenerate

```bash
./wire/proto/build.sh
```

This invokes `protoc` with `-I wire/proto` and writes both
`chat_pb2.py` and `chat_pb2.pyi` into
`wire/src/tabula_wire/proto/v1/`.

### CI verification

```bash
./wire/proto/build.sh --check
```

Regenerates into a tmp dir and `diff`s against the checked-in copy.
Exits non-zero if `chat.proto` and the bindings have drifted apart.

### Smoke test

```bash
cd wire
python -m pytest tests/proto -v
```

## Using the bindings

```python
from tabula_wire.proto.v1 import (
    PROTOCOL_VERSION,
    ClientFrame, ServerFrame,
    Hello, UserMessage, EndSession,
    Welcome, AssistantToken, AssistantTurnEnd, ErrorFrame,
)

# Build a Hello frame to send right after the Noise handshake completes:
hello = ClientFrame(
    hello=Hello(
        protocol_version=PROTOCOL_VERSION,
        client_identity="tabula-cli/0.1.0",
    )
)
encoded: bytes = hello.SerializeToString()

# Parse a frame received from the wire:
incoming = ServerFrame()
incoming.ParseFromString(encoded_bytes)
match incoming.WhichOneof("payload"):
    case "welcome":
        ...
    case "token":
        chunk = incoming.token.text
    case "turn_end":
        reason = incoming.turn_end.finish_reason
    case "error":
        ...
```

Server and client implementations (sub-issues #20 / #27) are
responsible for wrapping these `bytes` values in a length-prefixed
frame and pushing them through the Noise transport.

## Length-prefix framing (for sub-issues that implement the loop)

Each direction of the Noise transport carries a sequence of frames.
**One frame** on the wire is:

```
+-------------------+----------------------------------------+
|  uint32 BE length |  <length> bytes of serialized proto    |
+-------------------+----------------------------------------+
```

- `length` is a 4-byte **big-endian** unsigned integer.
- A length of 0 is invalid; close the session with
  `ErrorFrame { code = PROTOCOL }`.
- A reasonable upper bound (e.g. 1 MiB) MUST be enforced to bound
  memory; values above the bound are a malformed frame.
- The `<length>` bytes are the output of
  `ClientFrame.SerializeToString()` (or `ServerFrame.SerializeToString()`)
  with no extra metadata.

This format is documented here so #20 (server) and #27 (client) agree;
the implementation lives in those sub-issues.
